## The knobs

These are `TrainConfig` field names. `train()` and the CLI also accept the
short spellings in the CLI column, so `mosaic` sets `mosaic_prob`. On the CLI
`mixup` is routed by task: classification batch mixing for classifiers,
`mixup_prob` for detectors. `perspective` has no CLI flag and is set from Python.

<aug-knobs />

The base default is the value on `TrainConfig` itself. Most families override
some of them, and [Defaults by family](#defaults-by-family) gives the values a
run actually starts from. For pictures of what each knob does, see
[Augmentations](/docs/train/augmentations).

Ranges in brackets are intervals, so `[0, 1)` includes 0 and excludes 1. The
classification knobs are checked when their pipeline is built and raise
`ValueError` outside their range. The detection knobs are not checked by
`TrainConfig`, so an out-of-range value trains silently. The exceptions are a
drawn scale of 0 or less and a negative `perspective`, which raise `ValueError`
when a sample is warped.

## The three statuses

| Status | Meaning |
|---|---|
| `used` | The knob reaches the family's train pipeline and changes samples |
| `gated_by_mosaic` | The knob applies only to samples that took the mosaic branch, so with `mosaic_prob == 0` it never fires |
| `ignored` | The knob never reaches the pipeline; setting it does nothing |

`ignored` is the one worth checking before a run, because nothing fails. The
CLI warns when an explicitly set training parameter is one the selected family
ignores, and the trainer warns when `mixup_prob > 0` cannot fire because the
family gates MixUp on mosaic and `mosaic_prob` is zero.

## Which family honors which knob

<aug-matrix />

Every covered family follows one of six pipelines. In the YOLOX-style pipeline
the per-sample preprocessing applies HSV jitter and flips, while the affine warp
and MixUp run only inside the mosaic branch. YOLO-NAS instead runs a per-sample
affine that is always on, ignores mosaic, and applies MixUp independently,
reusing `mosaic_scale` as the affine scale range.

The DETR-style pipeline is a pass-through transform with no mosaic. Its
photometric distortion, zoom-out and IoU-crop are recipe constants rather than
configurable knobs, which is why `hsv_prob` and the geometry knobs never reach
it. Classification uses `flip_prob` for horizontal flips and `flipud` for
vertical flips. Semantic scale jitter and HSV come from family class attributes
rather than config knobs, and restoration flips are coupled input-and-target
operations with a fixed 0.5 probability.

`no_aug_epochs` is honored everywhere, though what it turns off differs: mosaic
and MixUp for YOLOX-style, the affine and MixUp for YOLO-NAS, the strong
photometric and crop augmentations plus the learning-rate tail for DETR-style,
and auto-augmentation, erasing, MixUp and CutMix for classification.
Classification crop and flips remain enabled.

Where a family differs from the rest of its pipeline, the reason is one of these:

| Family | Difference |
|---|---|
| `rtmdet`, `picodet`, `rtdetr`, `rtdetrv2` | `flipud` ignored: their transforms have no vertical flip |
| `fomo` | `perspective` and `flipud` ignored |
| `ppyoloe` | `flipud` ignored: the source recipe uses a random 90-degree rotation instead |
| `yolo9`, `yolo9_e2e`, `yolo9_p2`, `yolo7`, `rtdetr`, `rtdetrv2` | `mixup_scale` ignored: their MixUp blends whole frames at a random ratio without rescaling either one |
| `gtr` | `mosaic_prob` and `mixup_prob` used, for the first `mosaic_epochs` epochs; `degrees`, `translate` and `mosaic_scale` shape the affine that follows the mosaic |
| `rfdetr` | `hsv_prob` ignored: the native pipeline has no HSV jitter |
| `ec` | `hsv_prob`, `degrees` and `translate` used, for `task="pose"` only; detect and segment use fixed photometric recipes |
| `dinov2` | The classification pack is used, for `task="classify"` only |

`ec` and `dinov2` are multi-task families, so a knob is marked ignored only
when every one of the family's trainable tasks ignores it. That keeps the CLI
warning from ever being wrong for one task while right for another.

Dome-DETR inherits D-FINE's transforms unchanged. The one thing it cannot take
is multi-scale training, which its config disables rather than the
augmentation spec.

Thirty-one families are covered. For a family outside this list,
`ignored_aug_params` returns an empty set, so no warning is emitted for it.

## Defaults by family

The value each detection family's config starts from. An empty cell means the
family ignores that knob, so its default changes nothing.

<aug-defaults />

Two patterns matter more than any single value. RT-DETR, RT-DETRv2, PicoDet and
FOMO start with `mosaic_prob=0`, so on those families the knobs marked gated
in the matrix do nothing until mosaic is turned on. YOLOv9 starts with
rotation, shear and MixUp off and with `mosaic_scale=(0.5, 1.5)`, where the base
default is `(0.1, 2.0)`.

EdgeCrafter reads `hsv_prob`, `degrees` and `translate` only for `task="pose"`,
so its row shows the pose defaults for those three.

Classification families start from the base defaults: `flip_prob=0.5`,
`flipud=0.0`, `scale=(0.5, 1.0)`, the family's own `crop_pct`, and
`auto_augment`, `erasing`, `mixup` and `cutmix` off.

## Family-specific knobs

Some families carry augmentation knobs on their own `TrainConfig` subclass
rather than on the base. The CLI does not expose these; set them through the
Python API.

| Family | Knob | Meaning |
|---|---|---|
| `yolo9`, `yolo9_e2e`, `yolo9_p2` | `copy_paste` | Copy-paste instance augmentation probability, `task="segment"` only |
| `yolo9`, `yolo9_e2e`, `yolo9_p2` | `copy_paste_mode` | Copy-paste source: `flip` mirrors the same sample, `mixup` uses a second sample |
| `yolo9`, `yolo9_e2e`, `yolo9_p2` | `rot90` | Random 90-degree rotation probability |
| `rfdetr` | `copy_paste` | Copy-paste probability for `task="segment"`, `flip` mode only |
| `rfdetr` | `copy_paste_mode` | Copy-paste source mode for `task="segment"` |
| `rfdetr` | `crop_resize_prob` | Random crop-resize probability in the native pipeline |
| `dfine` | `crop_resize_prob` | Random crop-resize probability, `task="segment"` |
| `ec` | `crop_resize_prob` | Random crop-resize probability, `task="segment"` |
| `ec`, `yolonas` | `brightness_contrast_prob` | Brightness and contrast jitter probability, `task="pose"` |
| `ec`, `yolonas` | `affine_prob` | Keypoint-aware affine probability, `task="pose"` |

`rot90` applies to detect and OBB on `yolo9`.

## Querying the spec

| Helper | Returns |
|---|---|
| `aug_support(family)` | The knob-to-`Support` table, or `None` for an unknown family |
| `ignored_aug_params(family)` | The set of knob names the family ignores; empty for an unknown family |
| `uses_mosaic_gating(family)` | Whether the family's MixUp only fires on mosaic samples |
| `display_name(family)` | The human-facing family name used in warnings |
| `mixup_gating_warning(family, mosaic_prob, mixup_prob)` | The warning text when MixUp can never fire, else `None` |

A `Support` is a named tuple of `status` and `note`, where the note explains
why a knob is ignored or gated for that family. In 1.8.0 the spec still lists
`mixup_scale` as gated for the families that train through the YOLOv9 mosaic
wrapper, so `aug_support` reports it as gated there even though the matrix
above, which is checked against the pipeline, marks it ignored.

## The mosaic gate

For a YOLOX-style family, `mixup_prob=0.5` with `mosaic_prob=0` disables MixUp
entirely, because MixUp applies only to mosaic samples. That combination is
easy to reach when turning mosaic off late in training. The trainer logs a
warning naming the family, and `mixup_gating_warning` is the pure function
behind it.
